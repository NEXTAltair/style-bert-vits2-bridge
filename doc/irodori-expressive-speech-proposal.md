# Irodori専用の読み上げテキスト生成

- Status: Accepted / implemented locally; host patch and deployment required ([ADR 0007](adr/0007-irodori-expressive-speech.md))
- Date: 2026-10-17

## 要望

Irodori-TTSを使うとき、表示用の返答をそのまま読み上げるだけではなく、Irodori対応の絵文字注釈を含む音声用テキストを作る。表示本文、声の学習データ、自動読み上げのON/OFFは別の責務として保つ。

## 推奨する基本方式

返答を生成するモデルが、同じ応答内で表示本文と音声専用本文を作る。プラグインは対応モデルの表現ルールを提供し、OpenClawの既存の音声専用本文機能を利用する。単語の正規表現による感情推測や、毎回の別LLMによる全文再生成を基本動作にはしない。追加のモデル往復は避けられるが、音声本文を出力する分のトークンと生成時間は増える。

```text
表示: 直ったよ。これで普通に使える。
音声: 😊 直ったよ。⏸️ これで普通に使える。
```

OpenClawへの出力例:

```text
直ったよ。これで普通に使える。
[[tts:text]]😊 直ったよ。⏸️ これで普通に使える。[[/tts:text]]
```

感情を一律に明るくせず、会話と文の意味に合わせて必要な箇所だけ注釈を付ける。平叙文に無理な演技を加えない。囁き・笑い・非言語音を毎回強制しない。

## 責務と適用条件

- OpenClaw: provider選択、personaとユーザー設定の解決、TTS起動可否、音声専用本文の分離、配信を担当する。プラグインがこれらを再実装しない。
- Bridge: Irodori対応表と生成ガイダンス、音声本文の注釈検証・保持、APIへの受け渡しを担当する。
- 対象: `irodori`。`speech-cpp`は対応Irodoriモデルであることを明示的に確認した場合だけ。SBV2や別モデルへ流用しない。
- 現在の実効providerを使う。rootの既定値だけで判断せず、persona・ユーザー設定・呼び出しごとの選択との整合を確認する。公開SDKから必要な情報を安全に取得できない場合はhost側の汎用拡張を分離提案し、内部API依存で埋めない。
- 有効化は選択可能にする。既存ユーザー全員の読み方をリリースだけで変更しない。設定名は `irodoriExpressiveText` (既定false)。hostの `prepareSpeechPromptContext` APIがない環境ではガイドだけ無効化する。
- `auto=off`を変更しない。`tagged`ではタグ自体が再生のトリガーになるので、単なる表示返答に無条件で音声タグを足さない。手動読み上げは明示された1回の範囲で扱う。

## 今回の対象・対象外 (確定)

2026-10-17、利用者が「Irodoriモデルの顔文字対応で Qwen系のト書きは今回対応しない」と明示。今回の更新はIrodoriモデルの本文内絵文字注釈に限定する。

- 対象: 対応するIrodoriモデルへの絵文字付き読み上げ本文の生成・受け渡し。speech.cpp経由でも、使用モデルが対応Irodoriである場合だけ適用する。
- 対象外: Qwen系のト書き・自然言語instructionsの自動生成、絵文字との相互変換、モデル横断の表現変換adapter。将来対応を今回の実装要件に含めない。
- Qwen使用時はこの機能を適用しない。既存の手動instructionsの転送や通常の合成機能は変更しない。
- 判定は実際の使用モデルに基づく。同じGUI/API/providerを使っていることだけを理由に、Irodoriの絵文字仕様を別モデルへ適用しない。

## 絵文字の選択方針 (確定)

2026-10-17、利用者が「顔文字はなるべく幅広く使えるものを使う方針にして」と指定。少数の無難な絵文字へ絞らず、対応する表現を幅広く使う。

- 意味が公開されている45種すべてを自動生成の候補にする。生成ガイダンスにも全候補と意味を伝え、笑顔・優しさ・間など数種類だけの固定リストに縮めない。
- 感情、話し方、話速、非言語音、音響効果まで、文脈に合うものを幅広く選ぶ。特殊な表現も、必要な場面では選択対象にする。
- 幅広さは種類の選択肢を広げることで確保する。毎回同じ注釈へ偏らせず、一方で乱択や全種消化のノルマ、一文への大量投入で種類数を稼がない。
- 実装リストにのみある追加11種は、見た目から意味を創作しない。公式情報や検証で意味・効果が確認できたものを自動生成候補へ追加できる構成にする。既存の明示入力は全56種を保持対象とし、自動選択の意味付き候補と区別する。

## 本文の契約

1. 既に明示された読み上げ本文・絵文字を優先し、再推測や二重注釈をしない。
2. 初期版は元の語句を維持した注釈追加を基本とする。事実、数値、否定、条件、固有名詞を変えず、要約や口語化は別の明示的な機能として扱う。
3. 上記の選択方針に従い、公式に意味が記載された45種すべてを自動生成候補にする。少数の定番だけへ狭めず、追加11種の未知の意味は推測しない。
4. 注釈はまず1個ずつ台詞と同じ行に置く。連続絵文字や絵文字だけの行はホストの装飾除去で失われる場合がある。ZWJとvariation selectorを保持する。
5. 文字数上限を守る。ホストによる要約・切り詰めで注釈と本文が壊れないことを試験し、読み上げ専用文だけを無制限に長くしない。
6. 生成・検証に失敗した場合は元の読み上げ文へ戻し、同じ声で読む。勝手な別providerへの切替、TTSの有効化、追加のモデル呼び出しはしない。
7. 原文・変換後全文を標準ログへ保存しない。デバッグ用previewは利用者が明示的に要求した場合に限定する。

## 自動変換を保証する場合の追加方式

基本方式はモデルによる音声専用本文の生成に依存する。固定通知、直接API、`/tts audio`、音声専用文がない過去の返答の再生にまで、自動注釈が付くと保証してはいけない。

これらにも必ず適用したい場合は、providerの合成前処理で未注釈の本文を変換する任意のrewriteモードを追加する。モデルへ全文の自由な書換えを頼むより、固定された文・位置に対する絵文字挿入計画を返させ、原文への適用をコードで行う方式を検討する。既存の明示注釈は再処理しない。

追加方式には、別の推論待ち時間、費用、使用モデルの選択、本文の送信先に関する判断が必要になる。未知の外部サービスへ勝手に送信しない。共通の短いtimeoutと元文へのfallbackを用意し、同じ入力の二重変換を防ぐ。基本方式との優先順位と適用範囲を決めてから実装する。

## 確認した現行コードと残る実装検証

- `src/compatible-speech.ts`: Irodori/speech.cppのpayloadは現在 `input: req.text`。自動注釈生成はない。
- `src/index.ts`: `registerIrodoriExpressionHook`でopt-inのprompt hookを登録する。公開SDK不足は別添hostパッチで補い、通常合成は旧hostでも維持する。
- OpenClaw公式docs `tools/tts/commands.md`: `[[tts:text]]...[[/tts:text]]` による音声専用本文を定義している。
- 現行OpenClaw source `src/tts/provider-types.ts` / `tts-synthesis-support.ts`: `prepareSynthesis` はprovider確定後に `text` を変更できる。受け取る契約には会話履歴がないため、そこで会話文脈を知っていると仮定しない。
- prompt拡張の公開hook、実効TTS設定の取得、published SDKとの互換性は実装時に型と実ホストで検証する。登録成功だけを動作成功とは扱わない。

## 受入試験

- 表示本文に音声専用注釈が混入せず、Irodori APIの `input` には期待する絵文字が届く。
- 文脈に合う注釈、注釈不要の平叙文、明示注釈の優先、二重注釈防止を検査する。
- 意味付きの自動生成候補とガイダンスが45/45を含み、入力保持対象は56/56であることを集合照合する。感情・話し方・話速・非言語音・音響効果の異なる文脈を試し、定番数種類だけに固定されていないことを確認する。乱択や毎回の全種使用は合格条件にしない。
- 数値・否定・条件・固有名詞が維持される。
- Qwenを含む非Irodoriモデル、SBV2、機能OFFでは従来の動作を維持し、絵文字付与・ト書き生成を行わない。既存の手動instructionsを変えない。
- auto off / inbound / tagged、persona・provider切替、長文処理、変換失敗を検査する。
- 手動TTS・通知・過去返答で対応する経路と未対応経路を明示する。
- 同じ声・同じ文・同じseedの注釈あり/なしを試聴し、API通過とWAV生成成功を聴感上の改善と混同しない。
