# Irodori Production

「これを素材にしてモデルを作って」「声はそのままで、暗い話し方を明るくして」のような依頼を制作操作へつなぐ。利用者にCLIやパラメーター選択をさせず、目的に合う方法を選び、成果物と試聴候補を返す。

## まず決めること

| 依頼 | 操作 | 成果物の意味 |
|---|---|---|
| この素材の声で読んで | `create` → `audition` | 参照音声による声プロファイル。重みは学習しない |
| 素材からモデルを作って、話者を学習して | `create` → `train --plan` → `train` | まずSpeaker Inversion。基盤を固定して学習する話者埋め込み |
| 話し方が暗い、明るく、ゆっくり | `tune` → `audition --candidate` | 同じ声の表現・話速の別バージョン。再学習は不要 |
| 追加学習で声・表現を適応したい | `train --method lora` | 基盤と組み合わせるLoRA。埋め込みや参照キャッシュとは別 |
| 読みが変、固有名詞がおかしい | 対象の文・表記・分割を切り分ける | 声の不採用やLoRA再学習へ直結させない |

「モデルを作った」と言って参照プロファイルだけを渡さない。生成物が参照設定、話者埋め込み、LoRA、基盤重みのどれかを短く明示する。短い試験学習を品質完成と扱わない。

素材と目的が指定されていれば、新規コピー、別名の調整候補、試聴、明示された学習はその依頼の範囲で進める。既に受けた許可を聞き直さない。対象素材や「どの声を調整するか」が文脈からも分からない場合だけ、その一点を自然に聞く。既存物の削除・上書き、外部公開、クラウドへの素材送信、本番の既定声切替はこのスキルから自動的に導かない。

## 実行入口

このファイルのあるディレクトリを基準に、`../../scripts/irodori-workflow.py` を絶対パスへ解決する。wrapper自体はPython標準ライブラリのみ。推論・学習には既存Irodori環境のPythonを使う。npm経由では `sbv2-bridge irodori <command>` も同じ入口。

```text
python3 <plugin-root>/scripts/irodori-workflow.py status --irodori-root <Irodori-root>
```

`IRODORI_ROOT` または `--irodori-root` でソースを指定する。通常は既存 `.venv/bin/python` (Windowsは `.venv/Scripts/python.exe`) を発見する。違う環境は `--python` で指定する。Web UIのURLだけを根拠にAPIサーバーがあると決めつけない。制作にはHTTPサーバーの追加導入は不要。

素材の取り込み・転記形式・コマンド例は [workflow.md](references/workflow.md)。通常の依頼では必要な節だけ読む。

## 制作の不変条件

- 元音声と元モデルを変えず、新しい出力ディレクトリを使う。既存出力があれば別名を選ぶ。入力の由来・hash・台本を保持する。
- 複数話者が混ざる素材は対象話者を分ける。音声ファイルが同じフォルダーにあるだけで同一話者と仮定しない。
- 参照用の音声と、生成して試聴する音声を分ける。生成試聴を勝手に再クローン/学習素材へ戻さない。
- WAVだけでなく一般的な音声形式を取り込める。変換が必要ならFFmpegで新しいPCM WAVを作る。声の好みを勝手にノイズ/エコー除去へ置き換えない。
- 参照合計は120s以内。多数の素材は選別するか話者学習へ回し、黙って末尾を捨てない。学習は1clip30s以内を前提に、長い素材は元を残して発話境界で分割する。
- 学習用台本は同名 `.txt`、元manifestからの正確な転記、またはローカルASRを使う。音声を聴かずに台本を捏造しない。wrapperの自動ASRはloopback HTTPだけ。学習データをHugging Faceへアップロードする必要はない。
- Speaker Inversion/LoRAはv4/v4.1 Smallの公式configを使う。基盤モデルと成果物をセットで保存する。Large、旧版、継続学習はこのwrapperの実装済み範囲外なので公式手順を調べてから扱う。
- 長時間の処理は追跡可能なbackground実行を使い、出力先とlogを保つ。wrapperのjobは独自の `job.json` / `job.log`。SBV2のjobIdやtask APIへ架空のIDを渡さない。起動失敗/中断はlogとfailed receiptを確認し、成功に読み替えない。

## 調整と試聴

話し方だけの調整では基盤、参照音声、話者埋め込み、LoRAを固定し、captionと必要な話速だけを変える。captionはその依頼の文章から作る。特定利用者の人物像・声候補・好みをプラグイン既定値へ埋め込まない。

`--tone bright|calm|neutral` は一般的なcaptionの出発点であり、学習済みstyle名でも品質保証でもない。`--caption` なら既存の声質記述を必要に応じて残し、表現指定を整理する。速度は大きいほど速く、wrapperがIrodoriの逆方向の `duration_scale` へ変換する。

比較は複数の異なる短文で行い、それぞれの文はA/Bで同じtext・seedを使う。1文1WAV、A/Bプレフィックスで同じ試聴フォルダーへ。音声の一括連結、CSV/HTMLへの判定入力、候補の順位付けを利用者へ強制しない。削除による選別にも合わせ、削除済みファイルを元manifestから復活させない。

「明るい」を高い声や大げさな演技へ勝手に置き換えない。captionが効かない場合は参照の表現が勝っている可能性やモデルの制約を検討し、参照差替えは声の同一性にも影響すると分けて扱う。WAV/hash検査は破損検査であり、読み・声・感情の合格判定ではない。人間の試聴結果は `note` で別版として残せるが必須にしない。

## 日常TTSへつなぐ場合

`export` はIrodori公式APIサーバー向けのprovider設定案を出すだけで、適用しない。基盤checkpointと参照ファイルがAPIサーバー側にあることを確認する。別コンテナーのホストパスはそのままでは使えない。

同梱providerは `irodori` と `speech-cpp`。WAV全体を返す実装で、逐次再生ではない。speech.cpp側の音声キャッシュは処理済み参照の `voice.gguf`。公式Python側の元WAV/話者埋め込み/LoRAとは互換と仮定しない。GUIでモデルを替えた後は登録声と既定値を再確認する。声登録が消えていても元のcacheが消えたとは限らず、まず既存cacheの再登録を検討する。
